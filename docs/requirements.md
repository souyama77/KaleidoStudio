## 0. ドキュメントの目的

本書は、Kaleido Studio の要件を明文化し、以下を実現することを目的とする。

1. 開発中の仕様ブレ・迷走を防ぐ
2. 基本設計・詳細設計・実装・テストの基準点とする
3. メンター・レビュー担当者・採用面接時に、プロダクト意図と設計思想を説明可能にする

---

## 1. 概要

### 1.1 プロダクト概要

Kaleido Studio は、**絵を描くことに苦手意識を持つ人でも、幾何学・対称性・数理ルールの力を借りて、短時間で“それなりに美しい作品”を作れる Web アプリケーション**である。

ユーザーは、自由描画や幾何学モードを通じて、発想力や観察力に頼りすぎず、**「描けた」「面白い」「また触りたい」**という成功体験を得ることを目指す。

---

### 1.2 目的

本プロダクトの目的は以下の通りとする。

1. **絵を描くことに苦手意識を持っている人に、“描けた”“楽しい”という成功体験を提供すること。**
   - 左右非対称・構図バランス崩壊・光源表現への苦手意識を、幾何学・対称性・ルールによって補助する
   - 「センス」ではなく「仕組み」で見栄えを支える

2. **発想力がなくても描き始められるきっかけを提供すること。**
   - 真っ白なキャンバスを前に手が止まる状態を避ける
   - あらかじめ用意された描画モードから直感的に開始できるようにする

3. **幾何学・数学が好きな人にとって、美術表現への入口となるツールを作ること。**
   - 「絵は苦手だが、数式や規則性は好き」という層に対して、ビジュアル表現を数理構造の延長として体験させる

4. **開発者本人が、実務レベルの工程（要件定義〜設計〜実装〜テスト〜デプロイ〜運用）を一通り体験し、ポートフォリオとして提示可能なプロダクトを完成させること。**
   - 技術検証で終わらせず、ドキュメントを含む成果物として残す

---

### 1.3 背景

- 作成者自身、絵を描くことに強い苦手意識を持っている
  - 左右非対称になり、バランスの悪い絵になってしまう
  - 「光源を意識して描いて」と言われても、観察ベースの指導だけでは理解できず、数学的・論理的な説明を求めていた
- 一般的な美術教育では、「よく観察して描いてみよう」「光源を意識して陰影を付けよう」といった、観察力・感覚・センスに依存した表現が重視されることが多い
- しかし、作成者本人を含め、
  - 「生まれ持ったセンスがないと難しい」
  - 「正解が見えないまま感覚だけで描けと言われている」
  と感じ、心理的ハードルが高くなる層が一定数存在すると考える
- 特に影の表現については、
  - どこをどの程度暗くすればよいか分からず、練習のしようがない
  - 一方で、影はある程度ルール化・数理化できる余地があり、論理的な補助の価値がある
- SNS（X、Instagram など）ではビジュアルが重要である一方、テンプレート型ツールは「テンプレ感が強い」「他人と被る」「そもそも選べない」という別の課題を持つ
- 幾何学模様や対称図形は、数学的ルールによって形が決まりやすく、発想力よりも“仕組み”で見た目を担保しやすい

以上の背景から、本プロダクトは
**「センス・発想力前提の美術」と「数学・ルールで考えたい人」の間にあるギャップを埋めるツール**
として位置づける。

## 2. ターゲット・利用シーン

### 2.1 ターゲット

本プロダクトの主ターゲットは以下とする。

#### ターゲット1：絵に苦手意識を持つ人
- 左右非対称になりやすい
- 構図バランスが取れない
- 光源や影の付け方が分からない
- 「自分は絵が下手だ」と感じ、描くことを避けている

#### ターゲット2：発想が出てこない人
- 真っ白なキャンバスを見ると手が止まる
- 何を描けばよいか分からない
- テンプレートツールでさえ選択肢が多すぎて迷う

#### ターゲット3：数学・幾何学は好きだが、美術は遠いと感じる人
- 数式、構造、ルールで考えるのが得意
- 感覚頼りの美術には入りにくさを感じる
- 図形・対称性・フラクタルに興味がある

---

### 2.2 利用シーン

- 5〜10分程度のスキマ時間に、スマホまたはPCブラウザでアクセスする
- マウスまたは指で数回なぞるだけで模様を生成する
- 気に入った作品をSNS用画像として保存する
- ログインユーザーは作品を保存し、後から再編集・一覧閲覧を行う
- 将来的には 3D 表示や短動画化によって、作品表現の幅を広げる

## 3. 解決したい課題と提供価値

### 3.1 解決したい課題

| ID | 要件名 | 内容 | 関連する課題 |
|---|---|---|---|
| BR-001 | 絵が苦手なユーザーの成功体験 | 絵を描くことに苦手意識を持つユーザーが、5分以内に「それなりに見える」作品を1枚完成できること | 課題1 |
| BR-002 | 発想力不要の描き始め体験 | 題材や発想がなくても、モード選択や簡単なパラメータ操作だけで描き始められること | 課題2 |
| BR-003 | センスではなく仕組みによるバランス補正 | 手描きが左右非対称・アンバランスになりやすいユーザーでも、対称描画や幾何学的ルールで見た目のバランスを補正できること | 課題1 |
| BR-004 | 光源・影のルール化された補助 | 光源表現が苦手なユーザーが、光源位置指定や簡易陰影補助によって、一貫性のある見え方を得られること | 課題3 |
| BR-005 | 継続利用したくなる創作環境 | ログインユーザーが作品保存・再編集・ギャラリーを通じて、継続利用したいと感じられること | 課題1,2 |

#### 課題定義
- 課題1: 絵が苦手という自己認識
- 課題2: 何を描けばよいか分からない
- 課題3: 光源・影・構図が感覚的すぎて理解できない

---

### 3.2 提供価値

#### 3.2.1 機能的価値
- 絵が苦手でも短時間で作品を作れる
- 発想力ゼロでも、4つの描画モードから描き始められる
- 規則性のある美しさを“操作して理解する”体験ができる
- ログインユーザーは作品を保存・一覧表示・再編集できる

#### 3.2.2 情緒的価値
- 一本線から図像が立ち上がる驚きと楽しさを得られる
- 「自分にも描けた」という自己効力感を得られる
- 線画だけでも美しく感じられる構造美を楽しめる

#### 3.2.3 差別化要素価値
- プロ向けデザインツールではなく、**絵が苦手な人向けの幾何学アートツール**である
- 幾何学・対称性・円環・フラクタルといったモチーフを主軸にしている
- 将来的に 3D トーラス表示や短動画化により、体験を段階的に拡張できる

## 4. スコープ・非スコープ

### 4.1 スコープ

#### 4.1.1 対象プラットフォーム
- Webブラウザ上で動作するシングルページアプリケーション（SPA）
- PC / タブレット / スマートフォンの主要モダンブラウザ
  - Chrome
  - Edge
  - Safari
  - Firefox

#### 4.1.2 機能スコープ
- 描画キャンバス
- 基本描画ツール
- 以下の描画モード
  - Mirror Symmetry（対称描画）
  - Kaleidoscope（万華鏡）
  - Sacred Geometry（円環／トーラス系）
  - Fractal – IFS（反復関数系）
- 線の色・太さ・透明度の変更
- 背景色変更
- 画像ダウンロード（PNG）
- ゲスト利用（ローカル保存）
- ログインユーザー向け作品保存・一覧・再編集
- ログ機能
- エラーハンドリング
- 入力バリデーション
- レスポンシブ対応

#### 4.1.3 保存スコープ
- ゲストユーザー
  - 作品は端末にダウンロード保存のみ
  - サーバ保存は行わない
- ログインユーザー
  - 編集用データ（JSON）
  - サムネイル画像
  - 必要に応じて完成画像
  を保存対象とする

#### 4.1.4 動画・3Dスコープ
- 2D描画過程のタイムラプス生成（クライアント側）
- 3Dトーラス表示（Phase3）
- 3D回転アニメーションの短動画化（Phase3）

---

### 4.2 非スコープ

#### 4.2.1 プラットフォーム
- ネイティブモバイルアプリ（iOS / Android）
- デスクトップネイティブアプリ（Windows / macOS）
- オフライン専用アプリ

#### 4.2.2 機能面
- フォロー / フォロワー
- DM / コメントスレッド
- 通知センター（リアルタイム通知）
- マルチユーザー同時編集
- AI画像生成機能
- AIプロンプト入力による自動作画
- サーバ側での長時間動画エンコード
- サーバ側での動画長期保存

#### 4.2.3 課金・決済
- 本番決済
- サブスクリプション課金
- 売上計上・請求書発行
- リアルマネーによるコイン購入

#### 4.2.4 運用・サポート
- 24時間365日の監視体制
- コールセンター
- 専任サポート窓口

---

### 4.3 前提条件・制約

#### 4.3.1 技術的前提条件
- 原則としてオープンソース技術を利用する
- 開発環境は Docker を利用する
- クラウドインフラは低コストまたは無料枠で運用できる範囲から始める
- フロントエンドで幾何学模様生成の主処理を担う
- サーバ側は認証・保存・一覧・ログなどのバックエンド責務に限定する

#### 4.3.2 ビジネス制約
- 課金機能は実装しない
- 広告表示は行わない
- コイン・ポイントを実装する場合も、体験用に限定する

#### 4.3.3 開発体制上の制約
- 個人開発を前提とする
- 実装コストの大きい機能は Phase 分割する
- Must / Should / Could に基づいて段階的に開発する

## 8. 非機能要件

### 8.1 UX・操作性
- 初見ユーザーでも 3分以内に描画を開始できること
- 頻繁に使う操作は主要導線上に配置すること
- Canvas が常に主役となるUIであること
- スマホでは片手操作を考慮すること

### 8.2 性能・スケーラビリティ
- 主要画面の初回表示は極端に遅くならないこと
- MAU 50〜100 を前提に低コスト運用できること
- 将来的なユーザー増に対してスケール可能であること

### 8.3 可用性
- 小規模個人開発として無理のない範囲で運用できること
- 落ちても原因特定・復旧しやすい構成であること

### 8.4 セキュリティ
- 認証情報を安全に扱うこと
- 保存APIに最低限の防御（認可、レート制限）を持つこと
- ログインユーザーの作品データは本人のみアクセス可能とすること

### 8.5 ログ・監視
- エラーログを取得できること
- API実行ログを取得できること
- 復旧時に追跡可能な情報を残すこと

### 8.6 保守性
- 描画ロジックとUIロジックを分離すること
- 将来のモード追加や3D機能追加に耐えられる構造とすること
